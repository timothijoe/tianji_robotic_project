# 问题与决策日志：Wuji Glove 右手动作到左手 Wuji Hand

更新日期：2026-08-02

这份文档以实际推进顺序记录本次工作的上下文、观察到的现象、采取的验证方式、未采用方案与最终结论。它的目的不是替代源代码，而是避免后续人员再次从头摸索设备、网络、Studio、坐标系与可视化之间的关系。

## A. 初始目标与约束

### A.1 用户目标

目标不是只读取手套数据，而是形成以下能力：

1. 驱动和验证已有的实体 Wuji Hand；
2. 使用当前仅有的 Wuji Glove 采集手部动作；
3. 对右手手套数据做映射，得到左手机械手关节；
4. 能记录、重放、读取五个手指的关节位置；
5. 优先在可视化环境验证，之后才考虑接入实体手；
6. 工具应尽量小，操作步骤简单，后续只更换录制 MCAP 的路径。

### A.2 安全与授权边界

- 用户希望最终使用实体手，但当前阶段不能因为一个坐标/关节顺序猜测就直接下发连续控制。
- 真实手的驱动、手套 SDK、Studio 和离线转换是不同进程/会话，应避免把“可以可视化”误解为“可以安全上实体手”。
- 所以本次最终交付刻意停在离线 MuJoCo 可视化：脚本没有导入 ROS 控制节点，也没有调用实体手 SDK 命令。

## B. 实体 Wuji Hand：连接与最初验证

### B.1 官方 SDK 和 ROS 2 驱动

- 用户安装了官方 Debian 包：`wujihandcpp 1.8.0`。
- `wujihandros2` 在 ROS 2 Jazzy 环境中构建成功。
- 左手实体手已被 ROS 驱动识别，并通过 `/hand_0/joint_commands` 接收命令。

### B.2 “命令发了但没有看到移动”的检查

最初用户指出：没有看到关节移动，怀疑虽然命令发布了但手没有实际响应。

采取的验证不是只查看命令 Topic，而是使用低速、连续、可见的正弦摆动命令，观察拇指实际运动。用户随后确认看到了连续摆动，说明：

- ROS 通信链路可用；
- 左手硬件连接可用；
- 对应关节命令路径可用；
- 之后的“手套转手”问题不需要先怀疑手本体完全不可用。

### B.3 温度与驱动风险

曾尝试依赖软件诊断温度，但软件侧温度读数并不能作为唯一可靠结论；用户人工触摸确认硬件温度正常。

重要经验：

- 不要在 ROS 驱动已占用实体手时，又通过 SDK 向同一只手直接下发命令。
- 两个控制源会造成会话/控制冲突，且会让“是哪一个进程在发命令”难以追溯。
- 后续如果接入实时遥操作，应在现有 ROS 控制链路里增加安全层，而不是让新的离线脚本绕过 ROS 直接控手。

## C. Wuji Glove：物理连接、网络和会话问题

### C.1 USB 与网线的疑问

手套外观有 USB 和网线两个接口。初期分别尝试插 USB、网线，以及两者都插。指示灯出现过“亮一下后熄灭”的现象，因此一度怀疑供电或功率。

后续结论：不能仅根据 USB 连接或灯的短暂状态判断 SDK 通信成功。实际可用的数据链路来自网口配置和手套的网络服务；USB 可能承担供电等作用，但本次没有把 USB 当作可靠的数据接口来建立 SDK 通信。

### C.2 左右手套替换

现场曾从左手设备换为右手手套，并多次重新插拔。这里有两层“左右”必须分开：

- **物理手套的左右**：决定手套输出骨架的坐标含义、Studio Topic 名称和 retargeting 的输入手性；
- **机械手的左右**：决定最终要构造 `Handedness.Left` 还是 `Handedness.Right` 的目标关节命令。

本项目的实际组合是：**右手手套输入 → 左手机械手输出**。这正是后续必须显式镜像坐标的原因。

### C.3 IP 地址的发现与谨慎原则

用户在其他电脑的 Wuji Studio 配置中看到右手设备可能是 `192.168.10.151`。SDK 的某个属性曾显示 `.150`，但按实际端点连接的验证结果，正确可工作的服务端是：

```text
192.168.10.151:50001
```

PC 网口 `enp129s0` 曾配置地址：

```text
192.168.10.10/24
```

这个地址只加在主机侧同一网段，不会修改手套自身 IP。用户明确表示不希望随意改变设备 IP，因为其他电脑仍可能需要用 Studio 配置该设备；因此本次始终采用“让主机适配设备现有 IP”的策略。

### C.4 “没有返回信息是否正确”

部分探测命令没有产生直观输出。对此不能直接判定为连接成功或失败。最终的有效验证标准改为：

1. SDK 真正完成连接；
2. 读取到设备身份信息；
3. 持续收到结构正确的手部骨架帧。

最终证据：可以读取 21 个右手骨架关键点；设备序列号为 `WG1KA03260510008`，固件版本 `0.10.1`。

### C.5 Studio 与 SDK 的会话冲突

使用 Studio 时尝试独立 SDK 客户端，设备返回：

```text
Session already exists
```

这说明同一手套不允许 Studio 与独立 SDK 客户端并行占有通信会话。最终操作约定：

- 需要 Studio 可视化/录制时：只启动 Studio；
- 需要 `glove_recorder.py` 直接走 SDK 采集时：关闭 Studio 或确保 Studio 已断开设备；
- 已录制为 MCAP 后的离线转换和 MuJoCo 回放：不连接手套，因此可不受这个会话限制。

## D. Studio：能做什么、不能做什么

### D.1 Studio 的有效用途

Studio 成功安装、运行并显示右手手部模型。它适合：

- 检查网络和手套是否连通；
- 实时观察骨架/手形；
- 在可视化的同时录制 MCAP；
- 作为采集阶段的主要界面。

用户一开始在面板中没有找到诸如 `Hand model source` 的选项。最终的经验是：Studio 界面版本可能与说明不同，关键是添加/打开 Hand Skeleton 或 3D Hand Visualization 类面板，并选择 `/right_glove/hand_skeleton`；不应依赖某个特定旧版本文案。

### D.2 Studio MCAP 的实际内容

对用户提供的录制文件进行了 MCAP 元数据检查：

```text
/home/zhoutong/catkin_robotic_ws/august_ws/wuji-record-data/august_02/session_20260802_162909_764.mcap
```

其中关键 Topic：

```text
/right_glove/hand_skeleton
```

编码为 JSON，帧的 `frame_id` 为 `r_wrist`。录制中也可包含 `tip_poses`、`hand_joint_angles` 等 Topic，但本项目选择 `hand_skeleton` 作为 retargeting 输入，因为官方映射接口可直接接收 21 个 MediaPipe 风格关键点。

### D.3 为什么生成左手 MCAP 后 Studio 没有左手模型

将 20 关节轨迹导出成标准 `sensor_msgs/msg/JointState` MCAP 后，Studio 并没有自动显示左手模型。这不是导出程序一定失败，而是两类数据不同：

- Studio 的手套可视化面板期望的是手套骨架/对应模型源；
- 本项目输出的是一般 ROS 关节状态 `/joint_states`，需要有机器人模型和 TF/关节解释链才可能显示成机械手。

因此没有继续尝试用 Studio 硬塞左手机械模型，而转向仓库已有 MJCF 模型的 MuJoCo。这让“轨迹是否映射合理”的问题可以独立于 Studio UI 能力验证。

## E. 录制与数据文件方案

### E.1 直接 SDK 录制器

实现了小型 `glove_recorder.py`：Tkinter 窗口提供开始、结束两个按钮，读取手套骨架并保存 NPZ。其目的是在不依赖 Studio 的场景也能采集原始关键点。

该工具需要连接手套，因此遵循 C.5 的会话互斥规则。它不是当前 Studio-MCAP 流程所必需的工具。

### E.2 选择 MCAP 作为主输入

因为用户已在 Studio 成功录制，并希望可视化，主流程最终以 Studio 的 MCAP 为输入：

```text
Studio MCAP → mcap_to_left_qpos.py → 左手 NPZ → MuJoCo
```

好处：

- Studio 可保留原始可视化和录制；
- 转换完全离线、可重复；
- 同一个 MCAP 可以在转换规则更新后重新处理；
- 不会占用手套网络会话。

## F. 右手映射左手：最重要的排错过程

### F.1 初始实现

最初按官方 API 创建目标为左手的 retargeter：

```python
RetargetSession.for_hand(HandModel.WujiHand, side=Handedness.Left)
```

并把 `/right_glove/hand_skeleton` 读出的 21 个点直接输入。程序正常运行，也生成了 20 维左手关节向量；因此“文件可生成”不能证明坐标语义正确。

### F.2 异常现象

用户在 MuJoCo 对比时指出：靠近指尖的关节在 Studio 手套图中没有明显弯折，但左手模型的对应关节已经非常弯曲。

对未镜像输出文件的数值诊断显示：

- 食指到小指的第三关节常在约 `1.548` / `1.551 rad`；
- 第四关节约 `99.5%` 的帧接近上限；
- 即使手套姿态并不表示强烈屈曲，末端关节也被映射到异常高屈曲量。

这排除了“只是 MuJoCo 视觉连杆比例不同”的简单解释，提示输入坐标手性可能不对。

### F.3 调查坐标约定

官方手部坐标说明的要点：

- wrist X：径向方向；
- wrist Z：近端方向；
- wrist Y：右手朝掌面为正，左手朝手背为正。

因此右手转左手并不是只把 `side=Left` 传进 API 即可。对于以 wrist 坐标表达的关键点，需要显式镜像 Y：

```python
mirrored[:, 1] *= -1
```

X、Z 均保持不变。

### F.4 修正与证据

在 `mcap_to_left_qpos.py` 中加入：

```python
def mirror_right_to_left(keypoints):
    mirrored = np.asarray(keypoints, dtype=np.float32).copy()
    if mirrored.shape != (21, 3):
        raise ValueError(...)
    mirrored[:, 1] *= -1
    return mirrored
```

随后将 `retargeter.step(keypoints)` 改为：

```python
retargeter.step(mirror_right_to_left(keypoints))
```

修正后输出诊断例如：

| 关节 | 修正后范围（rad） | 贴近限位帧比例 |
| --- | --- | --- |
| 食指第 3 关节 | 0.729 – 1.148 | 0% |
| 食指第 4 关节 | 0.000 – 0.616 | 0% |
| 中指第 3 关节 | 0.652 – 0.897 | 0% |
| 无名指第 3 关节 | 0.306 – 0.505 | 0% |
| 小指第 3 关节 | 0.229 – 0.610 | 0% |

这与用户观察到的“指尖关节过弯”相一致，且消除了异常贴上限的情况。因此，Y 轴镜像被确认是关键修复。

### F.5 输出文件命名的含义

为了避免混淆，正确版本使用：

```text
*_right_to_left_wuji_hand.npz
*_right_to_left_wuji_hand.mcap
```

旧文件：

```text
*_left_wuji_hand.npz
*_left_wuji_hand.mcap
```

来自修正前的直接映射，只保留作问题对照，不能作为后续验证或实体控制输入。

## G. MuJoCo 可视化的实现选择

### G.1 为什么使用 MuJoCo

仓库的 `mujoco-sim/wuji_hand_description/mjcf/left.xml` 已提供左手模型，且 Tianji 工程环境已有 MuJoCo。因此选择最小路径：加载该模型，将 20 关节轨迹写入模型的 actuator/qpos 对应位置，然后 `mj_forward` 刷新画面。

这比重新在 Studio 配置机器人模型、TF、Panel 更直接，也更利于隔离“映射是否正确”的验证。

### G.2 回放器的行为

`mujoco_left_replay.py` 的设计特征：

- 读取形状 `(N, 20)` 的 NPZ 轨迹；
- 检查时间戳长度和关节数据是否有限；
- 从 MuJoCo actuator 的 `trnid` 建立关节 qpos 地址；
- 写入 `data.qpos` 后调用 `mujoco.mj_forward`；
- 不调用 `mj_step`，不引入动态控制器；
- 提供暂停、逐帧、重置、速度调节等键盘控制。

这意味着画面展示的是“关节位置运动学回放”，而不是带接触/力控制的物理仿真。它适合验证姿态和映射趋势。

### G.3 已知视觉差异

即使映射正确，Studio 手套手形与 MuJoCo 机械手也不会完全相同：

- Studio 渲染的是人手/手套骨架；
- MuJoCo 渲染的是机械手连杆和关节；
- 两者的连杆长度、零位、关节耦合和视觉模型不同。

所以判据应为：手指整体屈伸方向、相对时序和明显异常限位是否合理；不能要求指尖位置或弯曲外观一一重合。

## H. 一键脚本的迭代记录

### H.1 初版目的

用户希望以后只改 MCAP 路径即可获得可视化，因此实现：

```text
wuji-glove-recorder/visualize_right_glove_to_left.sh
```

顺序为：

1. `mcap_to_left_qpos.py`：右手骨架镜像、retargeting，写 NPZ；
2. `left_qpos_to_mcap.py`：可选的关节状态 MCAP 导出；
3. `mujoco_left_replay.py`：打开 NPZ。

输出文件与输入 MCAP 放在同一目录，不会覆盖原始录制文件。

### H.2 路径配置的调整

用户不希望每次传参，因此脚本顶部定义：

```sh
DEFAULT_MCAP_PATH="/home/zhoutong/catkin_robotic_ws/august_ws/wuji-record-data/august_02/session_20260802_162909_764.mcap"
```

后续只需修改这一个变量，再运行脚本。命令行传入路径仍作为临时覆盖方式保留。

### H.3 `sh` 与 Bash 不兼容故障

用户使用：

```bash
sh visualize_right_glove_to_left.sh
```

得到错误：

```text
set: Illegal option -o pipefail
```

根因：初版虽然有 `#!/usr/bin/env bash`，但用户显式用 `sh` 启动时，shebang 不生效，Ubuntu 的 `/bin/sh`（通常为 dash）解析脚本；脚本中有 `pipefail`、`[[ ... ]]`、`BASH_SOURCE`、`printf %q` 等 Bash 专用语法。

解决方式不是要求用户记住必须输入 `bash`，而是把脚本改为 POSIX `sh`：

- shebang 改为 `#!/bin/sh`；
- `set -euo pipefail` 改为 `set -eu`；
- `[[ ... ]]` 改为 `[ ... ]` 或 `case`；
- `BASH_SOURCE` 改用 `$0`；
- 移除 `printf %q`。

修复后已经实际运行：

```bash
sh visualize_right_glove_to_left.sh
```

成功生成修正后的 NPZ/MCAP，并启动 MuJoCo。

### H.4 干跑模式

可用：

```bash
sh visualize_right_glove_to_left.sh --dry-run
```

干跑会显示输入路径、预计输出路径和三条实际会执行的命令，但不写入文件、不启动 MuJoCo。适合在开始前检查是否改对 `DEFAULT_MCAP_PATH`。

## J. 下一阶段建议（尚未实施）

### J.1 先扩大离线验证样本

录制多组动作：张手、握拳、单指屈伸、捏合、缓慢自然手势。每次跑一键脚本并观察：

1. 只使用一个实体手控制源（推荐已有 ROS 2 驱动）；

5. 提供显眼的急停方式；
6. 先单关节、低速、小幅度验证关节顺序；

### J.3 保留原始数据

原始 Studio MCAP 是可重复转换的唯一依据。不要只保留输出 NPZ；若以后更新坐标变换、SDK 或关节限制，必须从原 MCAP 重跑。

## K. 快速故障索引

| 现象 | 首先检查 | 已知结论 |
| --- | --- | --- |
| 手套灯短亮后灭 | 网线、主机 IP、Studio/SDK 会话 | 灯状态不能单独证明数据链路 |
| SDK/Studio 不能同时用 | 是否出现 `Session already exists` | 同一手套会话被占用，关闭另一方 |
| Studio 有右手、左手机械手 MCAP 不显示 | Topic 类型与模型来源 | `/joint_states` 不会自动变成 Hand Skeleton |
| MuJoCo 指尖过弯 | 输出文件名是否含 `right_to_left` | 应使用 Y 轴镜像后的文件 |
| `Illegal option -o pipefail` | 是否运行旧脚本 | 当前脚本已支持 `sh` |
| 实体手不动 | 不只看 Topic，要做低速可见摆动 | 已验证 ROS 驱动可实际运动左手 |
| 需要改 IP | 先确认现有 Studio 配置 | 优先改主机网段，不改设备 IP |

## L. 实体 MCAP 回放的新增安全层（2026-08-02）

### M.2 两个实际问题及修复

1. **进程冲突检查误判自身。** 初版通过 `pgrep` 拒绝 ROS 驱动与另一份 SDK 回放进程；模式同时匹配到当前回放程序自身，导致连接设备前就错误拒绝。修复为排除当前 PID，但仍拒绝其他控制进程。这是消除自我误报，不是降低安全边界。
2. **SDK 左右手字符串大小写不同。** 第二次尝试已扫描并连接到机械手，却在使能前被左右手校验拒绝。代码按 ROS 习惯比较小写 `"left"`，而官方 Python SDK 的 `handedness_name()` 类型是 `"Left" | "Right" | "Unknown"`。SDK 版现严格检查 `"Left"`。

前两次均在使能和发送关节命令前安全退出；第三次才执行完整回放。不能把前两次错误理解为机械手异常。

### M.3 实测结论、验证和遗留注意事项

修复后 SDK 日志确认连接左手 SN `LQSQJL.260706.001`、固件 `1.2.1`；整段回放退出码为 0。这说明扫描、连接、手性校验、使能、实时命令发布和结束清理都走通。程序结束会关闭 publisher、disable 手并断开 manager；之后若切回 ROS，必须重新启动 ROS driver。

- 自动化结果为 **28 passed**。测试时应使用 `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1`；否则当前 ROS 环境自动加载 `launch_testing`，而 SDK 虚拟环境缺少其 `yaml` 依赖，会在测试收集阶段失败。这是测试环境耦合，不是回放功能错误。
- SDK 脚本目前复用了 ROS 脚本里的纯 MCAP 读取、范围校验和缓入插值函数；它不会启动 ROS 节点或发送 ROS Topic，但代码结构容易令人误解为两条控制链路混在一起。未来可把这些纯轨迹函数抽到独立公共模块；在此之前，严格按两个 `.sh` 入口选择控制路径。
- 任意时刻只能运行 ROS 或 SDK 中的一条实体控制链路，绝不可同时运行。
